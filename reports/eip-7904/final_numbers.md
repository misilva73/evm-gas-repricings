# EIP-7904 - final numbers after BAL optimizations

#### May 11th, 2026

## Methodology

### Selecting which Operations to Reprice

The operations selected for repricing in this EIP were chosen based on their estimated million gas per second (Mgas/s) performance. For this EIP, a performance target of **100 million gas per second** is chosen. With this performance target, we will be able to increase the base throughput of the chain by 5x from our current 20Mgas/s performance.

### Data Collection

The gas costs proposed in this EIP are based on the actual time each operation takes to run on the various execution clients. Similar to the methodology used in the Gas Cost Estimator project, we generate synthetic blocks that isolate and stress individual EVM operations.

Concretely, to benchmark a single operation, different blocks are created by varying the number of times the target operation is executed and by changing the parameter values to the operation. The EEST benchmark suite contains the tests used to generate these blocks.

Then, the Benchmarkoor tool is used to collect the needed metrics. This tool returns the total execution time of the block and the number of times each operation was executed. Each test block is run multiple times on each client to account for variability in execution time. The benchmark results used in this analysis comes from this compute [suite](https://benchmarkoor.core.ethpandaops.io/suites/881b06a7c78081c2) on top of `bal-devnet-3` spec.

#### Runtime Estimation

To estimate the runtime of a single operation from the total execution time of the corresponding synthetic blocks, a **Non-Negative Least Squares (NNLS) Linear Regression** is used. This model enforces that all coefficients are non-negative, thus ensuring execution time cannot be negative. The model estimates runtime as a linear combination of:

- **Constant term (intercept)**: Base overhead for executing the test, which includes setup and teardown time
- **Operation count (slope)**: Number of times the operation is executed in the test. This parameter is the one that allows us to estimate the per-operation runtime.
- **Operation-specific parameters**: Variables like number of rounds, message size, or number of pairs

For simple operations (i.e., without additional parameters), the model estimates: `runtime = intercept + slope × operation_count`

For variable operations, the model estimates: `runtime = intercept + slope × operation_count + param1_coef × operation_count × param1 + param2_coef × operation_count × param2 + ...`

Independent models are created for each client and operation. Only operations and parameters with good model fits (R² > 0.5 and p-value < 0.05) are included in the gas cost proposal to ensure the reliability of the estimates.

The report with the model performance by operation and client can be accessed [here](./runtime_estimation/2026-05-01_2026-05-11_final/runtime_estimation_autogenerated_report.md).

#### Conversion to gas costs

New gas costs are calculated using the same target performance of 100Mgas/s. The formula used is:

```
new_gas = (anchor_rate * runtime_ms) / 1000
```

Where `runtime_ms` is the estimated runtime in milliseconds from the regression models.

The report with the full details of this step can be accessed [here](./runtime_estimation/2026-05-01_2026-05-11_final/new_gas_proposal.md).

## Results

In this section, we focus on the worst-case proposal (i.e., the maximum estimated cost across clients for each operation) and how sensitive it is to the slowest client.

### Operations that do not require a cost increase

Out of the 18 (opcode, parameter) pairs we [targeted initially](included_operations.md), 8 already run at or above the 100 Mgas/s target on the worst client. For these operations, the current gas cost is sufficient (and in several cases substantially overpriced relative to the anchor).

|Opcode|Parameter|Current Gas|Worst Gas|Worst Client|
|:---:|:---:|---:|---:|:---:|
|ADDMOD|constant|8|8|erigon|
|BLS12_G1ADD|constant|375|82|reth|
|BLS12_G2ADD|constant|600|114|reth|
|DIV|constant|5|5|erigon|
|ECADD|constant|150|104|reth|
|ECPAIRING|constant|45000|9372|reth|
|ECPAIRING|num_pairs|34000|10196|nethermind|
|KECCAK256|msg_size|6|1|besu|

**Key observations:**

- The BLS12-381 precompiles (`BLS12_G1ADD`, `BLS12_G2ADD`) and the alt-bn128 precompiles (`ECADD`, `ECPAIRING`) are overpriced by a factor of 3-5x relative to the 100 Mgas/s anchor. These could be repriced downward, but doing so is out of scope for this EIP.
- `ADDMOD` and `DIV` already sit at the anchor under the slowest client's runtime, so their current cost requires no change.

### Operations that require a cost increase

The remaining 10 (opcode, parameter) pairs have a worst-case estimate above the current gas cost. The table below shows the worst client alongside the second-worst client.

|BLAKE2F|constant|0|reth|38|besu|0|inf|

**Key observations:**

- **Erigon dominates the worst case** for 9 of the 10 operations that would be repriced. For the precompiles `ECRECOVER`, `P256VERIFY`, and `POINT_EVALUATION`, the worst-to-second-worst ratio is between 3.9x and 6.4x, meaning Erigon is several times slower than the next-slowest client on these operations.
- The only operation where the worst case is not driven by Erigon is `BLAKE2F constant`, where `reth` is the sole client with a measurable per-call runtime. The other four clients all round to 0 gas.
- For every operation in this list, **the second-worst client's estimate is at or below the current gas cost**. In other words, if we excluded the slowest client per operation, no operation in EIP-7904 would require a cost increase.

### Discussion: pricing by worst vs. second worst

The two tables above point to a striking pattern: the entire case for raising any gas cost in EIP-7904 rests on the performance of Erigon (and, in one case, the per-call cost on Reth for `BLAKE2F`). We would expect Erigon to show a performance closer to Geth, as their implementation for these operations is very similar. Thus, this performance difference either comes from some issue in how we are benchmarking Erigon on Benchmarkoor or a genuine performance mismatch between Erigon and the other clients.

If Erigon were optimized to perform within the range of the second-slowest client on these operations, the worst-case estimate for every affected opcode would drop to at or below the current gas cost, and no repricing-upward would be necessary to hit the 100 Mgas/s anchor.

Concretely, we see two paths forward for the final EIP-7904 specification:

1. **Reprice upward at the worst client.** This is the conservative path captured in the autogenerated proposal. It guarantees the 100 Mgas/s target is met on every client today, at the cost of raising fees on operations whose underlying cryptography is not actually slow. This would mean increases ranging from +4.9% to +100% on 9 operations.
2. **Coordinate with the Erigon team on targeted optimizations** for the affected operations, and reprice only those operations that remain above the anchor after optimization. Under this path, we would expect most or all of the increases listed above to become unnecessary.

We do not claim that Erigon-side optimization is guaranteed to close every gap. Some of the ratios above (e.g., 6.36x on `P256VERIFY`) are large enough that they may indicate a structural difference in the underlying library. However, the pattern is clear enough that we recommend exploring path (2) before locking in the increases from path (1), especially for the precompile operations where the proposed costs are most sensitive to a single client's runtime.
